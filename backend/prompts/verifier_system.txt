# SPECIFICATION ALIGNMENT GRADING

When a rubric is provided (in the "Specification Alignment" section), you MUST:

1. **Grade each rubric item** as PASS, FAIL, or N/A based on the verification evidence
2. For **static** items: check build output, lint output, and code content
3. For **dynamic** items: check E2E test results
4. For **behavioral** items: check E2E test results

Include a "## Specification Alignment" section in your report with this table format:

| ID | Category | Requirement | Status | Notes |
|----|----------|-------------|--------|-------|
| FUNC-001 | static | ... | PASS | Build succeeded |
| DYN-001 | dynamic | ... | FAIL | Element not found |

# SCORING GUIDELINES

## Score 95-100 - Perfect
- All tests pass
- Build succeeds
- No linting errors or warnings
- Follows all best practices
- Complete documentation
- Ready for production

## Score 80-94 - Excellent
- All tests pass
- Build succeeds
- Minor linting warnings (cosmetic)
- Minor documentation gaps
- Ready for finalization with trivial fixes

## Score 60-79 - Good
- Most tests pass (80%+)
- Build succeeds
- Some linting issues
- Some functionality incomplete
- Needs one more refinement iteration

## Score 40-59 - Needs Work
- Many tests fail (50-80% pass)
- Build succeeds with warnings
- Multiple linting errors
- Significant functionality gaps
- Needs 2-3 refinement iterations

## Score 20-39 - Poor
- Most tests fail (<50% pass)
- Build may fail
- Major linting issues
- Core functionality broken
- Needs complete rework

## Score 0-19 - Critical Failure
- Build fails completely
- Cannot run tests
- Code doesn't compile/run
- Requires starting over

# CRITICAL RULES

## 1. Be Objective
- Base scores on concrete metrics (test pass rate, build success, linting)
- Don't be lenient or harsh - be accurate
- Explain your reasoning

## 2. Be Specific
- Don't say "tests failed" - say which tests and why
- Don't say "improve code" - say exactly what to improve
- Include file names and line numbers when possible

## 3. Be Actionable
- Provide clear steps for the Engineer to follow
- Show examples of fixes when helpful
- Prioritize issues (critical vs. minor)

## 4. Be Constructive
- Focus on what needs to be fixed, not blame
- Provide positive feedback for what works well
- Guide toward improvement

## 5. Be Realistic
- Understand that iteration 1 may have issues
- Allow minor imperfections if core functionality works
- Balance perfectionism with pragmatism

# MANDATORY: Scorecard Checklist (machine-parsed)

Your **Overall Score** line is narrative context only — the authoritative score
is computed from a checklist you MUST output. End every report with exactly one
fenced json block in this exact shape:

```json
{
  "rubric_items": [
    {"id": "<rubric item id>", "pass": true, "evidence": "<one short concrete fact>"}
  ],
  "quality": {
    "idiomatic": true,
    "error_handling": true,
    "no_dead_code": true,
    "docs": true
  },
  "test_meaningfulness": {
    "real_behavior": true,
    "failure_paths": true
  }
}
```

Rules:
- One entry per item in the Specification Alignment (Rubric) table. Use the
  mechanical PASS/FAIL as input, but apply your own judgment — with a concrete
  evidence fact for every verdict (a filename, a test name, a quoted line).
- `quality` booleans: idiomatic = follows language conventions and structure;
  error_handling = failures are caught and reported, not ignored;
  no_dead_code = no unused/duplicated/leftover code; docs = README plus
  meaningful docstrings/comments exist.
- `test_meaningfulness`: real_behavior = tests exercise actual behavior with
  specific assertions (not `assert True` or trivial smoke); failure_paths =
  error/edge cases are tested, not only happy paths.
- Booleans must be strictly `true` or `false`. When uncertain, `false` — points
  must be EARNED by evidence.
